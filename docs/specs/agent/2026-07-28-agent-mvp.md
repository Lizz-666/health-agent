# Phase 5 Agent MVP

> Status: Gate 0 accepted at `f6c2eae59c784398fbf1ae38967be3c2ee720940`,
> 2026-07-29. This specification
> defines a personal-development wellness Agent, not a medical assistant or a
> public-release privacy/compliance conclusion. Runtime implementation is not
> authorized outside the gated implementation plan.

## Outcome

A signed-in user can open the Agent from the main navigation or from a current
training task, ask the product to explain owned structured state, and request a
small set of existing health/posture/training operations. Button and chat flows
call the same application services and deterministic safety engine.

The Agent is a server-controlled orchestration layer. The model may classify an
intent and select from a server-provided read allowlist. It returns structured
message/rationale codes, not user-visible free prose; the server renders all
text from reviewed templates. The model cannot choose its identity, expand its
permissions, execute a write, confirm for the user, call arbitrary SQL/HTTP, or
replace deterministic safety and validation.

## Non-Goals

- No diagnosis, treatment, rehabilitation, emergency triage, disease-specific
  exercise, nutrition recommendation, or unrestricted health question answering.
- No new health threshold, contraindication, training-load rule, exercise
  catalog content, or safety policy. Phase 3/4 policies remain authoritative.
  Phase 5 may encode existing safety-boundary signal names only as a
  conservative pre-provider routing list; a non-match is never classified safe.
- No automatic same-day shortening, deferral, recovery substitution, multi-day
  restructuring, or adaptive progression. Those remain Phase 7 work.
- No plan activation, plan cancellation, posture-goal confirmation, health
  profile mutation, safety-signal resolution, or photo analysis through Agent
  Tools. Existing dedicated product flows retain those responsibilities.
- No raw SQL, arbitrary HTTP, dynamic code execution, client-supplied `user_id`,
  model-selected Tool registration, or prompt-defined authorization.
- No complete-chat persistence, conversation history API, cross-device chat
  sync, semantic/vector memory, embeddings, retrieved web content, attachments,
  voice, streaming, or background autonomous runs.
- No direct display of model-authored free text. Phase 5 uses model output only
  as a strict intent/Tool/message-code decision and renders reviewed templates.
- No live AI call in unit tests, integration tests, CI, fixtures, screenshots,
  or phase acceptance. No real health data or production credentials.
- No public deployment, legal/compliance approval, or proof that a configured
  external provider is suitable for production health-data processing.
- No platform-wide account-deletion repair for independently owned health or
  training records. Phase 5 extends the current posture-owned deletion
  orchestration only for Agent-owned rows; broader account deletion remains
  explicit platform debt.

## Approved Task 0 Decisions

1. **Narrow same-day scope.** Phase 5's roadmap phrase `当日小调整` means only
   orchestrating Phase 4's existing one-per-day user substitution and structured
   feedback. Automatic shortening, deferral, or recovery behavior is not moved
   forward from Phase 7.
2. **Every write requires explicit confirmation.** The Agent turn may create a
   typed, short-lived proposal. A separate authenticated confirmation request
   executes it. This stricter MVP rule applies to check-in, weight, plan-draft
   generation, substitution, and feedback even where the product safety boundary
   would permit an automatic same-day action plus notification.
3. **Safety is not a model Tool.** Risk classification and plan validation are
   mandatory server wrappers around relevant reads/proposals/execution. The
   model cannot call, skip, reorder, or provide their result.
4. **Privacy-gated provider.** `AGENT_RUNTIME_ENABLED=false` by default. A live
   cloud provider additionally requires reviewed provider configuration, an
   active server-side `agent_cloud_processing` consent for the current disclosure
   version, and a satisfied Agent privacy gate. The global switch alone never
   authorizes a model call.
5. **No transcript memory.** User text and assistant prose exist only in the
   request/response and Flutter in-memory session. They are not stored in the
   database, ordinary logs, traces, analytics, or crash reports.
6. **Persistent minimal audit.** Store consent, run metadata, Tool event metadata,
   and short-lived typed write proposals. Do not store raw user text, assistant
   prose, raw health context, photos, URLs, prompts, or model responses.
7. **Four main destinations.** The Flutter bottom navigation becomes `今日 / 计划
   / Agent / 我的`. The old posture home remains available as a secondary
   `/posture` route and an Agent quick action; Phase 5 does not remove the posture
   workflow.
8. **Provider-neutral core.** The orchestrator depends on a typed provider
   protocol and deterministic fake. One live adapter may be implemented behind
   the privacy gate after its current official API is verified; provider details
   do not leak into domain services or client contracts.

## Users And Scenarios

- From an exercise card, a user opens Agent with a server-owned exercise/session
  reference. The Agent can explain the current prescription and offer an allowed
  replacement proposal based on current Phase 3/4 data.
- From Agent home, a user asks what today's training is. The server resolves the
  owned active plan and returns a bounded explanation.
- A user requests a new four-week plan. The Agent proposes the existing Phase 4
  draft-generation request. Confirmation calls `training.service.generate_draft`;
  plan activation still happens only in the existing Plan review flow.
- A user asks to record today's check-in, weight, training feedback, or one
  substitution. The turn returns a typed diff; no write occurs until the user
  taps confirm.
- A restricted/red-flag/missing-data/stale-context case receives deterministic
  blocked or clarification behavior. The provider cannot override it.
- A prompt-injection request asking to ignore policy, use another user ID, call a
  hidden Tool, activate a plan, or reveal internal prompts is rejected without a
  side effect.
- When the provider is disabled, unconfigured, unconsented, timed out, malformed,
  or over the step limit, the result is an explicit unavailable/invalid state.
  Existing button flows remain available.

## Architecture And Trust Boundaries

```text
Flutter user action
  -> JWT-authenticated Agent API
  -> deterministic safety-text pre-router
  -> server ActorContext + privacy gate
  -> Context Resolver (owned, minimal, typed)
  -> deterministic pre-gate / entry allowlist
  -> bounded Provider decision (untrusted)
  -> schema validation + Tool Registry authorization
  -> read Tool OR persisted write proposal
  -> deterministic post-gate / response envelope

explicit Flutter confirmation
  -> JWT-authenticated confirmation API
  -> owned proposal + idempotency + latest context
  -> existing domain service + deterministic safety/validator
  -> atomic audit/result update
```

`ActorContext` and `AsyncSession` are server-injected and never represented in
provider-visible Tool arguments. The provider receives only the allowlisted Tool
schemas for the current entry and a privacy-minimized context view. Domain
services remain callable without the Agent or provider.

Before any provider call, a versioned deterministic pre-router normalizes the
Chinese-first user message and checks conservative terms corresponding only to
the existing safety boundary: pain/injury, numbness, weakness, dizziness, chest
discomfort, and acute trauma. A match returns a fixed route to the dedicated
structured check-in/safety flow, calls no provider, and creates no proposal.
Negation or instructions to ignore a term do not suppress a match. A non-match
is explicitly `no_text_signal_detected`, never `normal` or a safety clearance;
latest structured domain gates still run. The model may additionally raise a
safety code, but its failure to do so cannot override the deterministic route.

## Entry And Context Contracts

`entry_type` is a closed enum. `entity_id` is required only where shown and is
always ownership-validated before context or Tool descriptions are assembled.
Missing and cross-user identifiers use the same non-enumerating result.

| Entry type | Entity | Minimal provider-visible context | Allowed capability families |
| --- | --- | --- | --- |
| `general` | none | readiness codes, current risk/gate code, active-plan/today presence | bounded cross-domain reads; permitted proposals only after clarification |
| `health_profile` | none | profile completeness/version, bounded categorical summaries, today's structured check-in state, trend summary | profile/check-in/weight reads; check-in and weight proposals |
| `posture_issue` | owned/current `issue_id` | catalog issue metadata, owned assessment source/severity/certainty codes, confirmed-goal flag | issue/profile/guide/priority reads only |
| `training_plan` | owned `plan_version_id` or current | version/status/rationale codes, schedule summary, validation/gate code | draft/active/today reads; draft-generation proposal |
| `training_session` | owned current `session_id` | local-date session, prescription IDs, structured feedback/substitution state, latest gate code | today/exercise reads; feedback/substitution proposals |
| `training_exercise` | owned current session + prescribed `exercise_id` | current prescription and versioned catalog explanation/stop-condition codes | exercise/today reads; substitution/feedback proposals |

The resolver loads identity from JWT and data from current services. It does not
accept profile fields, risk tier, Tool names, policy versions, consent, plan
fingerprints, or authorization claims from the client.

Every `POST /turns` request requires a non-empty IANA timezone accepted by the
existing `training.context.validate_iana_timezone` helper. The server derives the
local date from its UTC clock plus that validated timezone and never substitutes
a server/device default. Missing or invalid timezone returns `invalid_timezone`
before context resolution, provider execution, Tool execution, run/proposal
persistence, or any domain write. This uniform requirement also covers
`general` and `health_profile`, whose allowed reads can resolve today's state.

Excluded from provider context:

- phone/email/token/secret, other user IDs, database IDs unrelated to the entry
- raw profile/check-in/weight payloads when a bounded code/summary is sufficient
- free-text pain notes or symptoms, raw allergy/restriction text, consent records
- photo/object keys, signed URLs, original images, raw model results
- full historical records, complete plan JSON, complete chat history
- internal prompt text, stack traces, SQL, infrastructure or secret metadata

The canonical context fingerprint covers owned entity references, structured
versions, current safety decision, and proposal-relevant values. It is a keyed
HMAC-SHA256 using a dedicated server-only Agent audit key, contains no raw user
message, and is recomputed before write execution. Plain hashes are forbidden
for low-entropy health values because they are enumerable.

## Tool Registry And Permission Matrix

The registry is static code. Each entry binds a stable Tool name to a typed
Pydantic input/output, allowed entry types, side-effect class, confirmation rule,
authorization adapter, and deterministic pre/post validators. Unknown Tools and
unknown fields are rejected (`extra="forbid"`).

Every read adapter returns two separately typed projections: a minimal
`provider_view` and an owned `display_view`. Exact values needed only for the
user interface (for example a weight value or full prescription) can be rendered
by a server template without being sent back to the provider. The registry, not
the model, defines both projections. A Tool result is never automatically copied
into the next provider message.

| Tool | Class | Existing implementation reused | Agent behavior |
| --- | --- | --- | --- |
| `get_health_profile_summary` | read | `health.service.get_profile_result` | privacy-minimized summary only |
| `get_today_checkin` | read | `health.service.get_today` | current owned day only |
| `get_weight_trend_summary` | read | `health.service.get_weight_trend` | bounded trend summary, not full history |
| `list_posture_issues` | read | `posture.tools.list_posture_issues` | public catalog metadata |
| `get_posture_issue` | read | `posture.tools.get_posture_issue` | catalog detail/stop codes |
| `guide_posture_self_test` | read | `posture.tools.guide_posture_self_test` | owned prerequisites; no result write |
| `get_posture_profile` | read | `posture.tools.get_posture_profile` | owned structured result |
| `get_posture_priorities` | read | `posture.tools.suggest_posture_priorities` | suggestion only; no goal confirmation |
| `get_training_draft` | read | `training.service.get_draft` | current owned draft |
| `get_active_training_plan` | read | `training.service.get_active` | current owned active version |
| `get_today_training` | read | `training.service.get_today` | latest gate and effective daily state |
| `get_training_exercise` | read | `training.service.catalog/_index`, backed by `training.knowledge` | reuse the same verified versioned catalog and `_exercise_view` projection source; only catalog IDs referenced by owned context; no new data-access path |
| `upsert_today_checkin` | proposal/write | `health.service.upsert_today` | ordinary `abnormal_pain=false` structured check-in only; explicit diff + confirmation |
| `create_weight_record` | proposal/write | `health.service.create_weight_record` | explicit value/time, forced `note=null`, confirmation |
| `generate_training_plan_draft` | proposal/write | `training.service.generate_draft` | creates/replaces pending draft only after confirmation |
| `substitute_today_exercise` | proposal/write | `training.service.record_substitution` | one current-day revalidated substitution after confirmation |
| `record_training_feedback` | proposal/write | `training.service.record_feedback` | structured current-day outcome after confirmation |

Not provider-exposed: risk classification, candidate generation, plan validator,
plan confirmation/activation, plan cancellation, goal confirmation, profile
mutation, safety-signal mutation/resolution, purge, consent mutation, arbitrary
history reads, photo analysis/upload, database or HTTP access. These are either
mandatory wrappers, separate product flows, or out of scope.

Agent check-in proposals cannot contain `pain_followup`, `pain_area`,
`pain_note`, or set `abnormal_pain=true`. A pain/symptom report receives a fixed
route to the dedicated structured check-in/safety flow. The Agent also refuses
to overwrite an existing same-day check-in whose `abnormal_pain` is true, so it
cannot erase a current safety signal. Weight proposals force `note=null`.

## Provider And Orchestrator Contract

The provider accepts a server-authored prompt version, one untrusted user message
(maximum 2,000 Unicode code points), a redacted typed context, and only the Tool
schemas allowed for the resolved entry. It returns one strict discriminated
decision:

- `answer`: reviewed `message_code` plus typed references to supplied facts
- `clarify`: reviewed `question_code` plus the missing typed fields
- `read_tool_call`: exactly one allowlisted read Tool + typed arguments
- `action_proposal`: exactly one allowlisted write Tool + typed arguments
- `unsupported`: reviewed boundary `message_code`

Limits per HTTP turn: maximum four provider decisions, four read Tool calls, one
write proposal, and no parallel Tool calls. A write proposal ends orchestration.
The provider receives only the Tool's registry-defined `provider_view` as
untrusted structured data and cannot access `display_view` or change the
registry for the next step.

The server uses versioned deterministic response templates for every user-visible
message, including normal reads/explanations, clarification, unsupported scope,
restricted/red-flag decisions, missing data, privacy/provider failures, write
diffs, confirmations, and side-effect results. Provider output has no free-text
field. Open-ended medical/nutrition requests get a fixed wellness-boundary
response. No model-generated text can weaken or bypass these states.

Provider configuration is injected. Tests use a deterministic scripted fake.
The live adapter has an explicit connect/read timeout, no automatic write retry,
bounded response size, schema validation, and redacted logging. Its current
official API/tool-call behavior must be verified in the implementation Task;
floating SDK behavior is not assumed by this specification.

Server-only configuration has explicit defaults and is never client/model input:

- `AGENT_RUNTIME_ENABLED=false`
- `AGENT_PROVIDER_ID` and `AGENT_MODEL_ID` empty until reviewed/configured
- `AGENT_DISCLOSURE_VERSION` empty until matching Flutter disclosure exists
- `AGENT_AUDIT_HMAC_KEY` empty, secret, and required by the privacy gate
- `AGENT_AUDIT_HMAC_KEY_VERSION` empty and stored beside every fingerprint

Changing the HMAC key/version invalidates and scrubs pending proposals before
new runs are accepted. Old retained audit fingerprints remain opaque metadata;
the old key is not retained in Phase 5, so those fingerprints cannot be
re-verified during the remainder of their 30-day window. This bounded MVP audit
trade-off is accepted: old rows remain deletable but not cryptographically
comparable. Keys and provider credentials never enter the repository, responses,
logs, CI artifacts, or Flutter defines.

The text pre-router patterns live in versioned policy data tied to the current
`safety-boundaries.md` signal names. They add no severity threshold or medical
claim. Changes require safety review and synthetic normalization, negation,
obfuscation, and false-positive tests.

## Consent And Privacy Gate

Before any live cloud provider call, all conditions must pass:

1. global Agent runtime switch enabled
2. provider/model identity and processing boundary configured and disclosed
3. current disclosure/policy version available to Flutter
4. active server-side consent for `agent_cloud_processing`, current user,
   provider, and disclosure version
5. no raw transcript persistence and audited log redaction tests
6. user-accessible withdrawal and Agent-data deletion paths
7. provider failure leaves all non-Agent product flows available
8. requested entry/context is supported by the minimization contract
9. a dedicated non-default Agent audit HMAC key is configured server-side

Consent is never a model or Tool argument. Grant/withdraw endpoints are separate
authenticated product APIs. Withdrawal blocks new calls immediately, invalidates
and scrubs pending proposals, and clears in-memory Flutter conversation state.
Grant submits the provider/disclosure identifiers the user was actually shown;
the server requires exact equality with current configuration and returns
`agent_disclosure_stale` on a race instead of granting a newer unseen version.
These acknowledgement fields cannot select a different provider/model.
`DELETE /agent/data` removes the user's Agent proposals, Tool events, run audit,
Agent consent records, and shared idempotency rows in the
`agent_action_confirm`, `agent_consent_grant`, and `agent_consent_withdraw`
operation namespaces. It does not delete independently
owned health, posture, or training records or their domain idempotency evidence
created through confirmed operations.

The fake provider is injectable only from tests and has no runtime configuration
value or production/development selection path. It cannot be selected by client
input or used as evidence that the live privacy gate passed.

Backend E2E and Android smoke may launch a test-only FastAPI app factory from the
test harness with an injected scripted fake and synthetic seeded account. That
factory is not imported by production `app.main`, is not selectable by env/API,
and cannot satisfy or bypass the live privacy gate.

## Persistence And State

Migration `0008_agent_mvp.py` adds four narrowly scoped tables. All user FKs are
ownership-indexed and included in account/Agent-data deletion tests.

The repository has no account-deletion registration/discovery mechanism. Its
current `posture.purge` account-deletion path explicitly names posture tables and
shared idempotency rows, and does not currently delete independently owned
health/training domain rows. Task 2 therefore makes a reviewed cross-domain
extension to that existing orchestration: add all four Agent tables plus every
Agent operation namespace (`agent_action_confirm`, `agent_consent_grant`, and
`agent_consent_withdraw`) to its account-deletion path, including retry/resume
coverage. Phase 5 does not rename that posture-specific path as a platform-wide
purge and does not claim to close the pre-existing health/training deletion gap.

### `agent_cloud_consents`

- immutable consent events: `consent_id`, `user_id`, fixed `purpose`,
  `provider_id`, `disclosure_version`, `status` (`granted`/`withdrawn`),
  per-user `sequence_no`, `created_at`
- unique `(user_id, purpose, sequence_no)`; sequence allocation is serialized by
  the existing user lock
- the current active grant is the highest sequence; a later withdrawal
  invalidates every earlier grant without timestamp tie ambiguity
- no client-selected purpose/provider; the server binds current disclosure

### `agent_runs`

- `run_id`, `user_id`, unique `(user_id, client_turn_id)`, `entry_type`,
  `intent_code`, `context_fingerprint`, `prompt_version`, `provider_id`,
  `model_version`, `policy_version`, `fingerprint_key_version`, `status`,
  `result_code`, `tool_call_count`, `started_at`, `completed_at`, `expires_at`
- no user message, assistant message, raw context, prompt, or model response
- audit metadata retention is 30 days in Phase 5; expired runs and dependent
  Tool events are deleted by a global cleanup at Agent API boundaries and app
  startup, with the cleanup service independently callable/testable
- Phase 5 has no scheduler, so cleanup is best effort and not a guarantee of
  deletion exactly at 30 days when an instance has no startup/API traffic;
  public release requires a durable scheduled cleanup mechanism

### `agent_tool_events`

- `event_id`, `run_id`, `user_id`, stable `tool_name`, side-effect class,
  request fingerprint, `status`, `result_code`, optional domain `result_ref`,
  policy/context/fingerprint-key versions, timestamps
- no raw arguments or Tool result payload
- request/context/argument fingerprints are keyed HMAC-SHA256 with the dedicated
  Agent audit key, never plain hashes of low-entropy health values
- Tool events follow their parent run's 30-day retention and cascade cleanup

### `agent_action_proposals`

- `proposal_id`, `run_id`, `user_id`, stable `tool_name`, typed bounded
  `arguments_json`, `arguments_hash`, context/policy versions, `status`,
  fingerprint-key version, `expires_at`, optional `result_ref/result_code`,
  timestamps
- statuses: `pending -> executed | invalidated | expired | cancelled`
- expiration is 15 minutes; only `pending` rows retain arguments
- arguments are scrubbed (`NULL`) on every terminal transition, consent
  withdrawal, Agent-data deletion, and lazy expiry at turn/confirm boundaries
- arguments never contain free text, photos, secrets, actor IDs, or safety claims
- check-in arguments require `abnormal_pain=false` and no pain fields; weight
  arguments require `note=null`; existing abnormal-pain check-ins cannot be
  replaced by an Agent proposal

Agent confirmation reuses `idempotency_records` operation
`agent_action_confirm`. Same key + same proposal replays the recorded terminal
result; same key + different request returns `idempotency_key_conflict`; expired
anchors follow the existing `410` contract. Domain services that already require
idempotency receive a server-derived per-proposal key in their existing operation
namespace. Training writes therefore have both `agent_action_confirm` and the
existing `plan_generate`/`session_substitute`/`session_feedback` record. Health
writes have no domain idempotency layer and rely on `agent_action_confirm`, the
owned proposal lifecycle, user lock, and single transaction.

Current health services and training persistence commit internally, so an Agent
wrapper cannot claim atomicity by adding an outer transaction. Task 3 must
extract shared transaction-neutral internal operations for the five allowed
writes. Existing button/API wrappers continue to call those operations and then
commit as before; Agent confirmation calls the same operations inside one unit
of work that also records Tool event, domain/shared idempotency, proposal
terminal state, and result reference. No business rule is copied. A transient
exception rolls back and leaves the proposal pending/retriable; a deterministic
stale/safety/validation rejection is recorded in a separate owned terminal
transition with no domain write. Tests inject failure at every commit boundary.

## API Contracts

All routes are JWT-only under `/api/v1/agent`; request models forbid unknown
fields. No request accepts `user_id`, consent status, allowed Tools, risk tier,
policy version, context fingerprint, or server time. The consent-grant request's
displayed provider/disclosure identifiers are acknowledgement values validated
against server configuration, not provider/model selection.

| Method + path | Purpose | Key contract |
| --- | --- | --- |
| `GET /capabilities` | render runtime/provider disclosure and gate state | no provider call; no sensitive data |
| `POST /consents:grant` | explicit cloud-processing consent | `{accepted_provider_id, accepted_disclosure_version, idempotency_key}` must equal current server disclosure; otherwise stale error |
| `POST /consents:withdraw` | withdraw consent | `{idempotency_key}`; immediately blocks calls and scrubs pending proposals |
| `DELETE /data` | delete current user's Agent data | idempotent; does not delete domain records |
| `POST /turns` | process one ephemeral user turn | `{client_turn_id, entry_type, entity_id?, message, iana_timezone}`; timezone is required and validated with no default; duplicate turn ID returns prior structured status/proposal metadata without prose replay and never creates a second proposal |
| `POST /actions/{proposal_id}:confirm` | execute one owned pending proposal | `{idempotency_key}`; latest context/safety revalidated |
| `POST /actions/{proposal_id}:cancel` | discard one proposal | idempotent terminal transition and argument scrub |

`POST /turns` returns a typed envelope with `run_id`, `status`, `message`,
`result_code`, optional structured display data, and optional proposal
(`proposal_id`, Tool/action type, bounded diff, expiry). It never returns raw
context, internal prompt, provider response, consent record, or another user's
existence.

Stable failures include `agent_disabled`, `agent_consent_required`,
`agent_privacy_gate_blocked`, `agent_provider_unavailable`,
`agent_output_invalid`, `agent_step_limit`, `agent_tool_not_allowed`,
`agent_context_stale`, `agent_action_confirmation_required`,
`agent_action_expired`, `agent_action_invalidated`, `agent_disclosure_stale`, and the existing non-owner/
missing, `invalid_timezone`, idempotency, safety, and validation codes. Failures never become an
`answer`, successful write, normal/healthy result, or active plan.
`agent_safety_signal_route_required` is a deterministic non-provider response,
not a diagnosis or model failure.

## Write Confirmation Semantics

1. Provider proposes one typed action; schema and registry validate it.
2. Server computes current context/safety and a deterministic user-facing diff.
3. Server persists a 15-minute owned proposal; no domain write occurs.
4. Flutter displays Tool-specific values and an explicit confirm/cancel choice.
5. Confirmation loads and locks the owned proposal, handles idempotent replay,
   checks expiry/consent, rebuilds current context, and re-runs all domain gates.
6. Stale or newly unsafe context invalidates and scrubs the proposal.
7. The existing domain service executes. The proposal, Tool event, idempotency
   result, and domain result are committed in the shared transaction-neutral
   unit of work. Existing self-committing wrappers are not called from Agent.
8. Response displays the actual structured result. A generated plan remains a
   draft and still requires Phase 4's independent plan-review confirmation.

The model is never given `confirm`, `cancel`, consent, or data-deletion Tools.

## Flutter Product Contract

- Bottom destinations: `今日 / 计划 / Agent / 我的`; Agent replaces the old
  `首页` destination. `HomeScreen` becomes `/posture` and remains reachable by a
  clear posture quick action.
- `/agent` supports an in-memory message list, loading/unavailable/consent states,
  structured quick actions, typed proposal cards, diff, confirm/cancel, and retry
  that creates a new client turn ID only on explicit user action.
- Contextual routes pass only an entry type and entity ID. Exercise/session cards
  can open `/agent` with owned identifiers; no health payload is placed in route
  extras or logs.
- Logout, token failure, account switch, consent withdrawal, and provider reset
  invalidate Agent state immediately. App restart does not restore chat text.
- The UI identifies AI-assisted interpretation and provider boundary, uses fixed
  safety/error text for blocked states, and never labels an unavailable or
  unconfirmed operation as completed.
- Legacy `/` navigation redirects to `/posture`; existing posture/search/detail/
  self-test deep links remain valid and are covered by router tests.

## Safety, Failure, And Observability

- Every proposal and confirmation uses latest structured data. Red flag takes
  precedence and prevents generation/substitution/feedback execution where the
  existing domain service blocks it.
- Read results are ownership-scoped. Missing and cross-user entity IDs share a
  non-enumerating response.
- Provider/user/Tool text is untrusted. It cannot alter system policy, Tool
  metadata, actor, confirmation, step limits, or deterministic validators.
- Logs contain route, exception type, stable run/result codes, counts, and
  latency only. They omit user text, raw context/arguments/results, proposal
  payload, tokens, prompts, provider bodies, and health identifiers.
- Metrics are aggregate: run status, provider latency/failure, Tool/result code,
  proposal confirmation/cancellation/expiry. No per-user health dimensions.
- A provider failure before/after reads creates no write. A confirmation failure
  cannot leave a half-recorded domain side effect or a false executed proposal.
- Existing self-committing domain wrappers are refactored around shared
  transaction-neutral operations before Agent confirmation uses them; an outer
  transaction around a self-committing service is explicitly forbidden.

## Acceptance Criteria

1. From a current exercise, Agent resolves and explains the owned exercise and
   current session without client-supplied health data.
2. Unknown/cross-user entity IDs reveal no existence and execute no Tool.
3. Entry-specific allowlists reject hidden/unknown/disallowed Tools and fields.
4. Prompt injection cannot change actor, safety gate, confirmation, Tool schema,
   provider configuration, or maximum steps.
5. Existing safety-signal terms in user text route before provider execution,
   including negated/ignore-policy phrasing; a non-match is never a normal/safe
   conclusion.
6. Provider output contains no user-visible free-text field; all response text
   comes from reviewed versioned templates and unknown message codes fail closed.
7. Risk classification and plan validation are mandatory server code, never
   provider-selected Tools.
8. Chat and button plan generation call the same Phase 4 service/validator. Agent
   confirmation creates only a pending plan draft, never an active plan.
9. Check-in, weight, draft generation, substitution, and feedback have zero
   domain writes before explicit confirmation and exactly one after idempotent
   confirmation.
10. Agent cannot create or overwrite pain follow-up/free-text fields: pain reports
   use the dedicated safety flow, an existing abnormal-pain check-in is preserved,
   and weight notes remain null.
11. Confirmation revalidates current context; stale/restricted/red-flag changes
   invalidate the proposal and create no domain write.
12. Missing/invalid timezone and provider disabled/unconsented/timeout/malformed/
    over-limit paths return typed failures with no provider/Tool/persistence
    side effect and never normal, healthy, success, or executed state.
13. Live provider calls are impossible without the global switch, configured
    disclosure/provider, active current consent, and satisfied privacy gate.
14. Consent grant binds exactly to the provider/disclosure shown to the user;
    stale acknowledgement fails and grant/withdraw retries are idempotent.
15. Audit fingerprints use a configured server-only HMAC key and cannot be
    reproduced from low-entropy health values without that key.
16. Full chat, raw user message, assistant prose, prompt, provider response, and
    raw health context are absent from DB, logs, tests, and audit rows.
17. Proposal arguments expire in 15 minutes and are scrubbed on every terminal
    state, withdrawal, deletion, and lazy cleanup path.
18. Run/Tool metadata is eligible for deletion after 30 days and is removed by
    tested startup/request-bound cleanup; Phase 5 documents that this is
    best-effort without a scheduler. Consent lasts until Agent-data/account deletion.
19. Agent-data deletion and the existing posture-owned account-deletion
    orchestration remove all Agent user-linked rows and every Agent-namespace
    idempotency row. Agent-only deletion preserves domain records and domain
    idempotency; Phase 5 makes no broader health/training account-purge claim.
20. Flutter uses `今日 / 计划 / Agent / 我的`, preserves posture navigation and
    legacy `/` redirect/deep links, clears Agent state across accounts, and
    displays typed confirmation diffs.
21. The synthetic adversarial matrix, SQLite and PostgreSQL migration tests,
    OpenAPI/auth tests, Flutter tests, and Android business smoke all pass on the
    accepted exact SHA with no live AI call.

## Test And Evaluation Strategy

- Unit: context minimization, entity ownership, registry allowlists, strict
  schemas, consent gate, provider fake, step/tool limits, proposal state machine,
  argument scrubbing, keyed fingerprints, redacted audit/logging, deterministic
  safety-text routing, response templates, and unknown message-code rejection.
- Service/API: auth isolation, OpenAPI, duplicate client turn, proposal/confirm/
  cancel, idempotent replay/conflict/expiry, stale safety context, transaction
  rollback, provider timeout/malformed/partial failure.
- Migration: `0008` upgrade/downgrade on disposable SQLite and PostgreSQL 16,
  constraints/indexes, model metadata parity, cascade/purge behavior.
- Evaluation fixture: versioned synthetic cases for normal, caution, incomplete,
  restricted, red flag, cross-user, prompt injection, confirmation bypass,
  unknown Tool, excess loop, provider failure, and prohibited medical/nutrition
  requests. Expected results are stable codes/Tools, not prose snapshots.
- Flutter: model parsing fails closed, consent flow, ephemeral messages, proposal
  diff/confirm/cancel, contextual route, provider errors, logout/account reset,
  posture route preservation.
- Final: `python scripts/verify.py fast`, PostgreSQL-required full verification,
  `flutter analyze`, full `flutter test`, no-live-AI assertion, and Android
  login -> Agent -> contextual read -> proposal -> confirmation smoke using only
  synthetic data against the test-only injected-fake app factory.

## Rollout And Rollback

- Default rollout is off: `AGENT_RUNTIME_ENABLED=false` and no live call.
- Enable first in personal development after migrations, disclosure/consent UI,
  deletion/withdrawal, log tests, and Gate 3 acceptance. Use synthetic data for
  acceptance; real health data is outside automated development/evaluation.
- Operational rollback is the global switch. Existing Today/Plan/Posture/Profile
  flows continue without Agent.
- Before any real user data, verify provider terms, processing location,
  retention, and current official API behavior; update disclosure/version.
- Phase 5 audit metadata retention is 30 days; consent events remain until
  Agent-data/account deletion. Startup/request cleanup is best-effort rather than
  a deletion-at-day-30 guarantee; public release must independently reassess both
  and add durable scheduled cleanup.
- Migration downgrade is supported only on disposable/no-Agent-data databases.
  With retained Agent rows, rollback disables runtime and uses the documented
  Agent-data export/delete path before destructive schema downgrade.
