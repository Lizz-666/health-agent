# Phase 5 Agent MVP Implementation Plan

**Goal:** Deliver a privacy-gated, server-controlled Agent that reads existing
owned state and executes a bounded set of existing domain writes only after
explicit user confirmation.

**Spec:** `docs/specs/agent/2026-07-28-agent-mvp.md`

**Architecture:** Static typed Tool Registry + minimal Context Resolver + bounded
provider/orchestrator + persisted write proposals + separate confirmation API.
Domain services and deterministic safety/validation remain authoritative.

**Safety:** No model-selected safety gate, direct write, arbitrary SQL/HTTP,
photo path, plan activation, complete-chat persistence, or live AI in tests/CI.
Live provider calls require the global switch, current disclosure/provider, and
active server-side consent.

**Verification:** Focused tests per Task; Fast CI per implementation commit;
PostgreSQL Full CI at Gates 2-4; Flutter CI for client Tasks; final synthetic
adversarial evaluation and Android smoke.

> Status: Task 0 Gate 0 fixes pending independent re-review, 2026-07-29. Tasks 1-7 are not
> authorized until the spec/ADRs/plan pass Gate 0.

## CI Policy

- OpenCode may push only the named Phase 5 implementation branch and operate its
  draft PR/CI after Gate 0. It may not merge, force-push, change secrets/settings,
  deploy, or write `main`.
- Fast CI runs per Task. Full PostgreSQL is mandatory at Gate 2, Gate 3, Gate 4,
  and after base/rebase/conflict/schema/policy changes. Flutter CI starts with
  Task 5 and remains required thereafter.
- CI uses synthetic data, deterministic fake provider, immutable action pins,
  least permissions, concise artifacts, cancellation of stale runs, and no
  production secret or live model request.
- Evidence is valid only for the exact SHA. A material fix invalidates affected
  local/CI/device evidence.

## Rollback And Compatibility

- Tasks add new `/agent` APIs and tables; existing APIs remain compatible.
- Runtime stays disabled until Gate 3 and user consent; disabling restores the
  pre-Phase-5 operational surface without removing domain records.
- Migration downgrade runs only on disposable/no-Agent-data databases. Any
  retained Agent rows require explicit Agent-data deletion before destructive
  downgrade.
- Flutter must treat an older server without `/agent/capabilities` as Agent
  unavailable while preserving Today/Plan/Posture/Profile flows.
